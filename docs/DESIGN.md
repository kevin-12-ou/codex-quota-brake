# 设计说明

这份文档记录"为什么这么写"，尤其是那些**看起来可以更简单、但我们试过会坏**的地方。

## 1. 整体结构

```
每 10~60 秒一拍：
  读额度（app-server JSON-RPC，不花 token）
      ↓ 任一窗口 ≥ 阈值？
  判活（谁在真的生成）
      ↓
  二次确认（18 秒后再看一眼）
      ↓
  杀那个 app-server（taskkill /F）
      ↓
  记账（冷却 / 滑动窗口 / 已死 pid 黑名单）+ 桌面通知
```

状态机很浅：`OK ⇄ PAUSED`（episode），每次 `OK → PAUSED` 记一条 `episode start`，
回到阈值以下记 `episode end`。所有计数都用**滑动窗口**，不用"每个 episode 计一次"。

## 2. 为什么是"杀进程"，而不是点按钮

桌面 App 里确实有个"停止"按钮，但用 UI 自动化点它有三个硬伤：

1. 要靠截图/形状识别定位按钮，App 一改版就找不到（实测会打出 `NO-BUTTON: ... Nothing clicked.`）。
2. 抢前台、可能误点（把草稿发出去比不停更糟）。
3. 超阈值期间会每 10 秒重试一次，空转还刷日志。

而 app-server 是唯一"真正的执行者"：它是 Electron 的 stdio 子进程，**没有对外控制 socket**
（`~/.codex/app-server-control` 不存在，`codex app-server proxy` 直接报 `os error 10050`）。
所以从外部只能：**终止这个进程**。进程没了 → SSE 流断 → 回合结束。

代价与边界：
- 该 app-server 上**所有会话**的当前回合一起结束（不只是触发的那一个）。
- 线程本身持久化在 SQLite 里，`codex resume` / `codex queue` 能接着跑。
- 正在写的文件可能留半成品。

## 3. 判活：怎么才算"真的在生成"

只看"进程存在"会误杀空闲的 app-server（它常驻），所以用两条通道：

| 通道 | 判据 | 为什么 |
|---|---|---|
| 桌面 App | `~/.codex/logs_<n>.sqlite` 里该 thread **30 秒内 ≥2 行**、最新行 **20 秒内** | 生成中的回合每 0~13 秒落一行 trace；回合结束后该 thread 静默 |
| CLI | `codex.exe` 且命令行含 `exec`，且 18 秒内 CPU 增量 ≥0.3 秒 | `codex exec` 不写 thread 日志行，只能按进程看 |

**二次确认窗口 = 18 秒**，不能更短：回合里跑 `Start-Sleep` 之类的工具时日志会静默约 10 秒，
6 秒窗口会把真回合判成空闲（实测漏判过两次）。

**桌面通道不用 CPU 判据**：空闲 app-server 也会被 MCP 子进程带动 CPU，用它当判据会误杀。

被否掉的旧判据："45 秒内有过日志行就算活跃"。它会把刚被 `thread/resume` 的空闲线程当成在生成
（实测：某线程 74 秒只写 5 行，最近 30 秒 1 行，仍被判为活跃）。

## 4. 动手策略

| 机制 | 值 | 原因 |
|---|---|---|
| 冷却 | 30 秒 | 防止一拍内反复动手；也限制整体频率 |
| 滑动窗口 | 10 分钟内最多 20 次 | 早期版本是"每个 episode 最多 6 次"，实测连续尝试 6 次后**刹车自己罢工**（`kill-cap (6/6)`），反而没人守 |
| 同 pid 去重 | 是 | 同一 app-server 上两个线程同时跑，只应杀一次 |
| 已死 pid | 拉黑 1 小时 | 探活与动手之间 App 可能已经换掉 app-server；这种 pid 杀了也没意义，且不该占配额 |
| 只杀 `codex.exe` | 是 | 白名单校验，其它进程一律拒绝并记日志 |
| `--once` | 默认只判定 | "看一眼状态"不该顺手停掉正在干的活；要动手必须加 `--yes` |

### 软预警（warnAt）

硬停在阈值上，但**人需要提前知道**：到 `warnAt`（默认 80%）先弹一次通知，同一窗口周期只提醒
一次（按 `resetsAt` 去重，窗口重置后会重新提醒）。这样用户还有机会自己收尾，而不是被动挨一刀。

设计上刻意把"提醒"和"动手"分成两档：提醒可以晚一点、软一点；动手必须果断且只做一次判断。

> 关于"额度撞满会不会导致模型降级"：公开资料没有这个机制，本机 8 天日志里 `model_rerouted`
> 出现 0 次，自建指纹检测 10/10 正常。所以本工具的理由**不是**防降智，而是防"撞满后到重置前
> 无法工作"——这个代价是可验证的。

## 5. 读额度的稳健性

- `account/rateLimits/read` 偶发超时（实测过几次）。**一次失败就跳过整拍会留保护空档**，
  所以 3 秒后重试一次；仍失败才放弃这一拍。
- **绝不拿旧快照动手**：如果拿上一次的 95% 去杀，而窗口刚好重置成 0%，就会误杀新回合。
- 读额度本身不是模型请求，不消耗额度（实测：连续 60+ 次读取，百分比不变）。

## 6. 踩过的坑（都会静默失效，所以写下来）

1. **状态文件带 BOM** → `JSON.parse` 抛异常 → 冷却/上限全部失效。现在读之前先剥 BOM。
2. **两套同名配置键**（旧工具箱的 `maxKills` 被新引擎误读成 20 次/10 分钟）→ 配置键加前缀，各认各的。
3. **外部命令输出是 GBK**（`taskkill`）→ 按 UTF-8 解码是乱码。现在按 GBK 解码。
4. **日志无限增长** → 超过 8MB 自动截断。
5. **死锁接管**：`taskkill /F` 留下的锁（pid 已死）必须能被新实例接管，否则重启后不干活。
6. **状态文件被手改成非法 JSON** → 回落默认值继续工作，不崩。
7. **重复启动**（开机自启 + 手动）→ 单实例锁，第二个直接退出。
8. **心跳**：每 20 拍写一行 `tick #N 5h=..% weekly=..%`，否则"它在跑吗"只能靠猜。

## 7. 怎么测（不用花额度）

真依赖（模型请求、你的账号）会让"多轮测试"变得昂贵。做法是给它们做**行为等价的替身**：

```powershell
Copy-Item "C:\Program Files\nodejs\node.exe" .\faketurn\codex.exe   # 名字就是被测代码认的那个
Start-Process .\faketurn\codex.exe -ArgumentList '"burn.js"','exec' -WindowStyle Hidden
```

`burn.js` 只需要持续烧一点 CPU。于是它在刹车眼里就是一个"命令行含 exec 且 CPU 在涨"的回合，
**不联网、不调模型、零额度**，但走的判定与杀进程链路和真实回合完全一样。

另外留了纯数据注入点，用来把"判定"和"动作"分开测：

```powershell
node quota_brake.mjs --once --dry-run --json --fake-percent 95 --fake-weekly 95 --fake-active <pid>
```

已用这套方法覆盖：基线杀进程、并发两个回合、杀掉后再来一个、重启后接管、状态文件损坏、
日志截断、上限、冷却、去重、拒绝非 codex 进程、依赖读取失败（fail-safe）、pid 在动手前消失。

## 8. 复杂度预算

- 依赖：**0 个第三方包**（只用 Node 内置 + Windows 自带 `taskkill`/PowerShell）。
- 配置项：8 个，全部可热改。
- 维护面：一个 600 行的单文件 + 一个通知脚本 + 两个安装脚本。
- 刻意没做：跨平台、GUI、自动续跑（这类应该由 Codex 自己的队列/会话能力负责）。
